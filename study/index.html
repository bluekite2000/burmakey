Type Burglish, get Burmese script — at half the taps

A learning ranker turns the toneless Latin that Myanmar already types in chat into canonical Burmese Unicode. Measured on 19,898 held-out tokens of real text, it cuts typing effort roughly in half and removes Burglish’s ambiguity entirely.

Simulation on real corpus data. No user trials, no native-speaker review yet. Data: myG2P v2 and myPOS v3 (Ye Kyaw Thu et al., CC BY-NC-SA 4.0 — noncommercial).

−50.2% fewer taps per word than typing Burmese script character-by-character — while sending unambiguous Unicode instead of guessable Burglish.

The problem

Young Myanmar people type Burglish — Burmese in improvised English letters, no tones, no vowel length. It is marginally faster than hunting through a script layout, which is exactly why it spread. But it is lossy: across real running text, 67.7% of Burglish words are spelled identically to at least one other Burmese word. taja can be any of seven words; akyi seven; acha six. The reader guesses.

Meanwhile the decade-long Zawgyi/Unicode split left Burmese text that looks fine but sorts, searches and travels badly. A lexicon-driven input method emits canonical Unicode by construction, so it fixes both problems at once.

Headline result

Every system typing the same 19,898 held-out tokens.

  • −50.2% taps against script typing, −47.4% against Burglish — while ambiguity goes to zero.
  • Corpus pretraining helped here (+0.10 taps saved, zero-key prediction 14.7% → 17.9%) because training and test share register. Pretraining is not good or bad in itself; mismatched register is what hurts.
  • A 5-candidate shortlist beats 3 (2.58 vs 2.84 taps/word).
  • Only 1.2% of in-lexicon tokens had to be typed out in full.
  • Hard floor: an unrecognised word — a name, slang — is sent exactly as typed, so the keyboard can never be worse than the status quo.

Head-to-head against the keyboards people actually use

Bagan is the market leader, 10M+ downloads; TTKeyboard and Gboard Myanmar work the same way.

The fair comparison is not “our engine versus their keyboard.” So both sides were given the identical engine — frequency + recency + bigram, corpus-pretrained, 5-candidate bar — and only the input code was allowed to differ. Streams are held-out real sentences: chat (≤8 words, 800 messages) and essay (≥15 words, 200 sentences), about 4.7k words each.

Counting taps, the answer looks emphatic. But a tap is not a tap on a phone, so we re-ran the whole comparison on a modelled handset.

Second pass — the same test on a phone

Counting taps hides four things that matter on a handset, and they do not all point the same way:

  • Bagan was measured, not assumed. v14.62 was installed on an emulator and every key probed. Three corrections followed, and they do not all favour us: its layout is 10 columns, the same key width as Latin (an earlier guess of 11 handed us a Fitts advantage that does not exist); its base layer is assigned by alphabet order, not frequency, so 9.2% of real glyphs need a long-press rather than the 0.5% assumed; and Burmese script has no per-word commit tap — the model was charging one, inflating the competitor by a full tap per word. Net: substantially less favourable to us.
  • Glyphs that do not fit the base layer sit behind a layer switch costing an extra tap. In practice this barely matters: a 40-key base layer already covers 99.5% of real keystrokes. Nearly neutral.
  • A candidate-bar pick is one tap but not one key press — it adds a visual scan that grows with the candidate’s position, plus a long reach up to the strip. Both engine systems pay this on most words. Favours neither, penalises the tap-count framing.
  • Script characters carry more information per tap, so the script system reaches the right candidate in fewer keystrokes (2.33 vs 2.45). Favours the script keyboard.

So the second pass costs every system in seconds per word: each key press timed by Fitts’s law from the layout’s real key size and the actual key-to-key travel of the typed sequence, each candidate pick timed as a reach plus a position-dependent scan, and each mis-tap charged a notice, backspace and retap.

The phone model is less flattering than the tap count, and it corrects two earlier claims. Against Bagan as it actually exists, BurmaKey is about 32% faster, not the ~50% the tap count implied — because a candidate pick costs a scan that a tap count treats as free. Against a hypothetical Bagan carrying this exact engine, BurmaKey is not the “statistical tie” reported earlier: it is consistently 3–5% slower, in every one of the 81 parameter combinations tested. Script characters simply narrow the candidate list faster than Latin letters, and bigger Latin keys do not quite buy that back.

Both conclusions are robust in sign across the whole sweep, but the magnitudes move a lot — the advantage over real competitors ranges from −15% to −39% depending on how expensive you believe a visual scan is. Treat the direction as the finding and the size as an estimate.

What survives is the original point, sharpened: the engine is the product. The measured advantage comes almost entirely from prediction, not from the Latin input code. BurmaKey’s real edge over the hypothetical is the part this model cannot score — no script layout to learn (the Burglish generation already has Latin muscle memory), and free English↔Burmese code-switching without swapping keyboards. The product implication is unchanged and now better supported: ship both input modes over one engine.

Reproduce: python3 src/h2h_mobile.py --sweep. The cost model’s per-action constants are literature-shaped assumptions, not measurements of Myanmar users — which is why every headline above is given as a swept range. The BurmaKey tap figures reproduce the earlier study exactly (2.45 / 2.67); the two Bagan arms land slightly below the earlier run (5.10 vs 5.24, 2.33 vs 2.42) because the original head-to-head script was never committed and had to be rebuilt from its description.

Does it hold outside the news register?

myPOS is news and general text, but the keyboard targets chat. A simulated chat stream — 600 messages, 3,308 words assembled from conversational high-frequency vocabulary, with approximate word order — brackets that register from below.

Zero-key prediction collapses to 0.9% here, which confirms it derives from real syntax rather than from the lexicon: scramble the word order and the bigram prior stops paying. Real chat sits between this floor and the +18% measured on real sentences.

What happens after day one

The engine learns on the device. Every result above is a single pass with fresh state, so none of it can say what that learning is worth over weeks — or whether it goes wrong.

This section is deliberately not a competitor comparison. Simulated chatters cannot manufacture information about human behaviour; they can only resample corpus statistics we already have. What they can do is exercise the engine's own state over a horizon the single-pass test never reaches. Every number below is a statement about the engine's mechanics.

Setup. 24 simulated users, 20 days, 30 messages a day — 600 messages each, around four thousand scored words. Users are given different primary topics (derived by k-means over content-word tf-idf, since myPOS has no topic metadata) so their vocabularies genuinely differ. The bigram prior is pretrained on one half of the corpus; every user's stream is drawn from the disjoint other half and sampled without replacement, so no user ever types text the prior has seen, and nothing is scored twice.

Learning compounds; it does not saturate. The saving over the no-learning control grows from 6.1% on day 1 to 10.2% on day 20, still rising at the end of the run. The control stays flat (2.767 to 2.755), which is what tells us the improvement is the engine learning rather than the text getting easier.

This matters for how the product is described. “It learns your words” is not a first-session nicety — on this evidence the keyboard a user has had for three weeks is measurably better than the one they installed, and the gap was still widening when the simulation stopped.

Does a stale prior hurt after a topic change?

The obvious way to test this — compare users who switch topic against users who do not — is confounded: those are different people typing different text, so the difference measures topic difficulty, not switching. Instead all three arms below type the identical evaluation text and differ only in the history the engine carries into it.

A stale prior is harmless. Priming on the wrong topic lands within 0.0% of cold — the learned state neither helps nor gets in the way, and chunked results show it tracking the cold arm across the whole evaluation stream rather than recovering from a dip. What a topic change costs you is the benefit (1.8% when the history matches), not a penalty. That is the desirable failure mode: the engine degrades to its shipped prior instead of fighting you.

How much does this vary between users?

Across 24 users the mean ranges from 2.412 to 2.699 taps per word — a spread of 0.287, or 11% of the median. That is larger than the entire measured gap between BurmaKey and the hypothetical ideal-engine script keyboard (3–6%). Any single headline number for this keyboard, including ours, hides more variation than the design differences everyone argues about.

Does the state stay inside a phone-sized budget?

Growth is linear at 5.1 KB/day — about 1.8 MB a year — with no sign of levelling off by day 20 (940 recency entries, 2,909 learned prefixes). That is comfortable for a phone in year one and untenable forever, so the design needs a pruning policy before it ships. Nothing in the current engine has one.

Does the unbounded recency counter need a decay?

The shipped engine scores recency as a lifetime count (+10 per use) that never decays. That looked like a bug waiting to happen over thousands of words, so the same streams were replayed under two alternatives: exponential forgetting (half-life 200 words) and a hard cap at 5 uses.

This is a result worth recording precisely because it says do not fix it — the obvious hardening would have made the keyboard slower.

Reproduce: python3 src/longrun.py (24 users × 20 days × 30 msgs, seed 20260817, ~90s). These are engine mechanics measured on resampled corpus text — they say nothing about how real people behave, and the perfect-typist assumption from the earlier sections still applies throughout.

Method

myG2P provides 24,802 words with tone-marked romanizations. Mining its syllable alignments yields a 2,348-entry syllable→roman map plus a rule syllable-breaker (89.4% exact match against myG2P’s own splits), which romanizes 16,192 corpus words — 87.3% token coverage of real running text. A first iteration using the dictionary alone reached only 21.1% coverage, and its results were discarded as biased.

myPOS supplies 41,738 real segmented sentences: 39,738 for training (frequencies, bigram prior) and 2,000 held out for test (19,898 scored tokens). The input code is toneless Burglish — tone marks stripped from MLC-style romanization. Output is Burmese script, unambiguous by construction. The engine is a learning ranker over lexicon candidates (freq + 10·recency + 100·bigram, beam 50, 5-candidate bar). It carries no Burmese knowledge: only the lexicon and the romanizer are language-specific, together about 100 lines mined from existing CC-licensed resources.

What this does not show

  • Every number is simulation with a perfect typist — no typos, instant candidate recognition. No human has typed on this keyboard.
  • Picking from the suggestion bar happens on about 69% of words. That is a real attention cost, and taps do not price it.
  • 12.7% of tokens fall outside the romanizable lexicon and were skipped in scoring. The raw-fallback guarantee covers them in a real product, but they are not in these averages.
  • Burglish spelling in the wild varies more than tone-stripped MLC romanization. The variant normalizer in the web keyboard was derived from spelling logic, not from Burmese users, and needs native tuning.
  • The script-typing baseline is one key per codepoint. That is a fair approximation of layout keyboards but ignores shift-layer costs — which would worsen the baseline, not the engine.
  • myPOS is news and general register, not chat. The simulation above brackets it; it does not measure it.

Try it, then tell us what is wrong

The keyboard runs entirely in the browser — the 16,192-word lexicon, the prediction and the learning all stay on your device, and your message text is never sent anywhere. What the project needs now is not more engineering but Burmese eyes on the output.
